# Web Development course information

Last confirmed with the instructor: **2 September 2026**

## North-star goal

- At the end of the course, students should be able to decide when a web application is appropriate, then justify, design, implement, and debug a modular full-stack CRUD application.
- They should be able to explain the HTTP, security, performance, and architecture decisions behind their implementation in project work and written reasoning.
- Students commonly struggle to connect theory with code, trace browser-server exchanges, select HTTP methods and status codes, explain non-functional tradeoffs, and implement or debug independently.
- A strong performance traces a requirement through architecture and code, justifies the chosen technology and protocol behaviour, diagnoses failures using evidence, and communicates the reasoning clearly.

## Course character

- Teaching approach: problem and intuition first, followed by precise terminology and implementation
- Balance: concise explanations, worked traces, purposeful practice, and short reflection or explanation prompts
- Feedback tone: direct and explanatory; treat wrong answers as reasonable attempts and identify the governing rule
- Examples: realistic CRUD systems such as libraries, restaurants, ecommerce, blogs, or other student-selected project domains
- Terminology: use front end, back end, client, server, request, response, HTTP method, status code, CRUD, MVC, and non-functional requirement consistently
- Avoid: framework-first instruction, answer copying, generic praise, and interaction that only reveals text

## Teaching intent

- Platform role: ungraded companion for preparation, weekly exercises, and exam revision
- Course outcomes: justify web technology choices; trace and explain browser-server communication; design and implement dynamic front-end and server-side behaviour; build modular CRUD/MVC systems; diagnose functional, security, and performance problems
- Assessment relationship: formative support for graded work and the written exam; it contains no graded work
- Learner actions: predict, trace, classify, construct, diagnose, debug, compare, and explain
- Visible progression: orient students to the shared course path without points, streaks, locks, or implied mastery
- Practice strategy: embedded checks in study modules plus optional integrated revision practice on the same path once sufficient source material is available
- Practice formats: request-response tracing, message construction, method/status diagnosis, code and DevTools interpretation, design decisions, and short written explanations; avoid using MCQ for every target
- Feedback and retry: explain the rule and misconception, keep feedback visible until explicit continuation, allow retry and reset, and restore resolved feedback on revisit
