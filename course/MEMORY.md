# Course memory

This file is the durable, tool-independent memory for collaboration with the instructor. Every agent reads it before asking course questions or changing course content.

Last reviewed with instructor: **2 September 2026**

## North-star goal

- Students should be able to decide when a web application is appropriate, then justify, design, implement, and debug a modular full-stack CRUD application.
- Students should be able to explain the HTTP, security, performance, and architecture decisions behind their implementation.

## Learners and prerequisites

- The intended learners are software-engineering students with basic programming experience but little reliable prior knowledge of web development.
- Recurring difficulties to design for are connecting theory to code, tracing browser-server request and response behaviour, choosing HTTP methods and status codes, explaining non-functional tradeoffs, and working independently rather than copying an answer.

## Instructor's teaching preferences

- The platform is an ungraded companion for preparation, weekly exercises, and exam revision.
- Prefer learner actions such as prediction, tracing, debugging, and explanation over passive reveal or decorative interaction.
- The platform must not provide solutions for graded coding assignments or reproduce restricted exam material.

## Terminology, notation, and examples

- Use `CRUD` for Create, Read, Update, and Delete. Treat `CURD` in Lecture 1 as a source typo that needs correction in learner-facing material.
- Keep the course's front end, back end, client, server, request, response, HTTP method, status code, and non-functional requirement terminology consistent.

## Memory rules

- When a decision changes, update the active section and move the old entry here with the date it was superseded.
